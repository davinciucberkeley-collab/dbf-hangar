## W14-A advice: viewer GLB 404

Intent: T84 was meant to make `tests/test_viewer_static.py::test_propose_link_survives_real_git_side_effects` pass reliably on both runners, with no console 404 while Studio re-checks a design during edit and propose.
Actual: windows-latest failed twice on std/u4.12-t104 @ 5b31c07 (run 45300604062, attempt 1 `concept-a-49cecb0d2e55.glb`, attempt 2 `concept-a-e4bf93337309.glb`). Each time there was one 404, for the `.glb` only. The `.mass.json` and `.scorecard.json` of the same version, which the page fetches next, loaded fine.
Not caused by the branch: the file name is `<did>-<design_hash>` and `design_hash` (core/hangar/studio.py:47-56) hashes only `__version__`, the standards file, the schema and the design folder's file names, sizes and mtimes. ops/claims.py, README.md and docs/cli.md cannot change it.

Cause (reproduced locally, 1 of 1 tries). Tests leave Studio worker threads running, and those workers write into the next test's sandbox.
- `tests/test_studio.py::test_studio_set_changes_only_the_edited_line` (lines 129-150, both params) builds `studio.Studio()` (`_serve_studio`, line 123). It calls `design.set` on concept-a, and that op's `scan()` queues a check. The test then shuts down only the HTTP server. The daemon `_worker` thread (studio.py:136) keeps running the queued jobs after monkeypatch has restored the module globals.
- `_job_check` reads the module globals `DESIGNS_DIR` (studio.py:154) and `DATA_DIR` (studio.py:163, 173) when the job runs, not when the Studio was built. So when the next test (the propose test, same xdist worker) has re-patched them, the leaked worker checks the new test's `designs/concept-a` and runs its T84 cleanup on the new test's `data/`. Its `keep` set is its own fid and its own previous hash (studio.py:171-175), so it deletes the live Studio's newest files.
- `design_entry` writes the `.glb` first and the scorecard and mass about 50 s later (index.py:125-128). A leaked cleanup that lands in that window deletes only the `.glb`. The live check then publishes that version, and the page gets a 404 for the glb while mass and scorecard load. This matches CI.
- Trace (pytest on the branch tree with a tracing plugin from the scratchpad; no code edited), run as `test_studio_set_changes_only_the_edited_line` followed by the propose test in one process: `[170.24] Thread-7 export done concept-a-3a10860c110b.glb` (live Studio, check j2), then `[172.07] Thread-4 unlink test_propose_link_survives_rea0 concept-a-3a10860c110b.glb`. Thread-4 is the leaked worker of the `[crlf]` Studio. At 220.81 the page requested it, and the test failed with the CI message: `404 (Not Found) http://127.0.0.1:53514/data/concept-a-3a10860c110b.glb`. The same test alone passed (253 s, no foreign unlink).
- Why only Windows, and why twice on one SHA: the failure needs a leaking studio test to land on the same xdist worker just before this test, and its checks to overlap with this test's checks. `-n auto` load scheduling and the slower Windows runner (attempt 2 took 429 s against 294 s) make that overlap likely there. Scheduling, not the branch, decides it, so it can repeat on one SHA and skip others. It is a race between tests. It is not deterministic on this branch.
- T84: its change (keep the previous version for one more re-check) is harmless but aimed at the wrong race, so the T84 fix is incomplete. Its diagnostic (URL in `collect()`) is what made this diagnosis possible. The original T84 Windows failure (three 404s, run 45163693398) also fits this cause: a leaked cleanup that runs after all of a version's files exist deletes all three.

Options considered: subtract the T84 keep-previous logic (does not touch the cause, so not enough) / modify the tests so every Studio-building helper (`_serve_studio`, lines 78, 367, 392, `test_surfaces_in_sync.py:60`, `_start_studio`) drains its jobs before teardown (works, but each new test must remember it, and some drains wait about 50 s) / adjust the test order or set xdist `--dist loadfile` (hides it, not enough) / add a retry or ignore glb 404s in `collect()` (forbidden by T84's brief, and it hides real bugs).

Recommended fix (one): in `core/hangar/studio.py`, a Studio fixes its folders when it is built. `__init__` stores `self.designs_dir, self.data_dir, self.cache_file = DESIGNS_DIR, DATA_DIR, CACHE_FILE`. `scan` (with `self.designs_dir.glob("*/plane.yaml")` in place of `list_designs()`), `_save_cache`, `_job_check`, `_job_import_dbf`, `_job_fea`, `read_*`, `export` and the handler's `/data/` route (`studio.data_dir`) use those. A leaked worker can then touch only its own dead sandbox. No viewer change, and `assert errors == []` stays as it is.
Test that proves it (no browser, deterministic), in `tests/test_studio.py`: build Studio A in sandbox 1 and do not start its job yet (block the worker with a gate or queue a check after the re-patch). Monkeypatch `DESIGNS_DIR`/`DATA_DIR`/`CACHE_FILE` to sandbox 2, which holds `example-tailsitter-wing` and a sentinel file `data/example-tailsitter-wing-0123456789ab.glb`. Let A's check run, then assert that the sentinel still exists and nothing new appeared in sandbox 2's `data/`. Then show it fails on main's studio.py (R-b). Pass check: that test, `tests/test_studio.py` in full, and on CI the browser test green on windows, plus a local run of `tests/test_studio.py::test_studio_set_changes_only_the_edited_line tests/test_viewer_static.py::test_propose_link_survives_real_git_side_effects -m "" -p no:xdist` in that order, which reproduces the failure today.
