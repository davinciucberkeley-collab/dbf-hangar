### Security of the log hook
| Attack within `Bash(plane *)` | Result |
|---|---|
| Unset or repoint the variable (`PLANE_BENCH_LOG= plane ...`, `env ... plane`) | Not reachable: the command does not start with `plane `. |
| Skip logging by calling hangar another way (`python -m hangar.cli`, Studio, MCP) | Not reachable with only `Bash(plane *)`; every `plane` run goes through `main()`. |
| Spoof log lines (an op with an output path, e.g. `design export --out` aimed at the log) | Overwriting gives unparseable lines or rows without `argv`, so "unreadable" and fail. Well-formed fake lines cannot help either: a pass still means `designs/` equals a replay of plane commands from the snapshot. |
| Hide a direct write behind a read-only command | Read-only commands are skipped in the replay, so a file changed alongside one (e.g. by shell redirection) makes `designs/` differ and the run fails. |
| Tamper with the snapshot | Possible in principle: the snapshot is at `ws/../snapshot`, reachable by a relative path (`plane design set ../snapshot/designs/<id> ...`). Through plane commands this gains nothing (they are logged and replayed). With a non-plane write (shell redirection into both `../snapshot/...` and `designs/...`) snapshot and workspace would agree and the check would pass. That needs the harness to allow redirection on a `Bash(plane *)` command, which I could not verify offline. The bench.py:133 docstring ("so the agent's commands cannot reach it") overstates this. See follow-up 1. |

### Non-blocking suggestions (follow-ups for the conductor / advisor)
1. (major) Pin the snapshot: in `run_op`, hash `snapshot/` right after `snapshot_design` (kept in memory, not on disk) and have `replay` fail the run if it changed; or place the snapshot in a separate `mkdtemp` no workspace-relative path reaches. Fix the bench.py:133 docstring. Separately, probe once in a real bench run whether output redirection on a `plane` command is allowed under `Bash(plane *)`; if it is, that is a harness hole independent of T54.
2. (major) The replay runs every logged non-read-only command with the grader's full environment and no confinement: a logged `plane bench run` would start another paid `claude` run, `fea run` may hit the 600 s timeout, and commands whose path arguments point outside `ws` (the real repo, `DESIGNS_DIR`, `.sweeps` under the installed REPO_ROOT, or the snapshot) are applied there a second time. Consider an allow-list of replayable ops (those that write only under their path argument), with any other mutating command failing the run unexecuted. Related to T91.
3. (minor) Path mapping at bench.py:196 is a string replace on `str(ws)` and `ws.as_posix()`. A workspace path written another way (8.3 short name on Windows, different case, `../<run_id>/designs/...`) is not mapped, so the replay writes into the graded workspace instead of `replay/` and a legitimate run fails (fail-closed, but it mutates `ws` after grading).
4. (minor) An unwritable `PLANE_BENCH_LOG` path makes `plane` crash with a traceback (cli.py:589); acceptable under the bench, a one-line message would be clearer.
