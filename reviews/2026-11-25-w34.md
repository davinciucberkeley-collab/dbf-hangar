### Judgment on the conductor's question: `battery_usable_fraction` exported with status `user`
- Fact: `standards/operations.yaml` line 59-62 gives `battery_usable_fraction` `source: pending`; `opencae_export.py` writes it with status `"user"` and source `standards/operations.yaml#battery_usable_fraction`. The other standards-derived values (`mission_hover_min`, `mission_cruise_min`: team-constraint sources; `ultimate_factor`: ASTM/STANAG sources) are sourced.
- The builder followed the brief exactly (drone_spec table: "status `user`") and the brief follows the study (`u18.1/study.md` lines 57 and 74: "values taken from `standards/*.yaml` ... -> user"). Not a builder defect.
- Effect: OpenCAE ranks evidence `estimate < datasheet < measured < user` and takes the weakest of a metric's inputs (`OpenCAEModel-main/opencae/drone/spec.py:116`, read to judge, nothing copied). `user` is the strongest level, so a pending value labelled `user` never lowers the basis of the endurance/hover metrics it feeds; U18.1-3 plans to append "; basis estimate" from that basis (study line 114), so the provisional input would be invisible in the row.
- The criteria that bear on it: scorecard "Evidence and closure": "Give every figure a unit, a source and a status label ... mark an estimate EST" [J4#2] [J4#9]; CLAUDE.md "Thresholds live only in standards/*.yaml, each with a source or `pending`" (pending = provisional). Labelling a pending figure with the strongest status contradicts the first.
- The plan text (study + brief) and that criterion disagree, so per my stop rule this goes to **advisor**, not decided here. Option for the advisor: status `estimate` when the standards entry's `source` is `pending`, else `user`, applied to every standards-derived value in drone_spec (one helper; today only `battery_usable_fraction` changes). Should be settled before U18.1-3 (rows) merges.
