Then build `ClaimGraph(nodes, design)`; the constructor runs these checks and raises `ClaimGraphError` naming the node id on the first failure (in this order):
1. Duplicate id.
2. Every reference resolves: `claim.calc` names a `calculation` node; `claim.limit.ref`, every value of `calculation.inputs`, `claim.assumes`, `calculation.assumes`, every `cites`, `verifies` (of claim: requirement ids; of test: claim ids) and every `parameter.source` entry that starts with `SRC-` names a declared node, or is a `P:` id. A `P:` id that is not a declared node must resolve in the PDL when `design` is set (rule below), else `ClaimGraphError(f"{who}: unknown reference {ref}")`. When `design` is `None` (imported graphs) `P:` ids are not checked.
3. A claim without `calc` must have `value`.
4. A declared parameter with `value` whose id also resolves in the PDL raises `ClaimGraphError(f"{id}: constant shadows a PDL value")`.
5. Unit check (proofs/1 rule 4): for each `calculation.units[arg]`, take the input node's `unit` (a declared parameter, claim, or assumption node; for an undeclared `P:` id there is none); if both exist and differ (plain string compare) raise `ClaimGraphError(f"{calc id}: input {arg} expects {u1} but {ref} is in {u2}")`.
6. Cycles: following `claim.calc` then `calculation.inputs` that name claims; a cycle raises `ClaimGraphError("calculation cycle: A -> B -> A")`.
Warnings (list, never raise): a `claim.parts` entry that is not a component id of the design (only when `design` is set); a `source` with no `url`.

PDL path syntax for `P:<path>` (resolved from `design.data` at every call, nothing cached): segments separated by `.`; a segment is `name` (mapping key) or `name[sel]` where `sel` selects the list element under `name` whose `id` equals `sel` (any text except `]`); `name[0]` with an all-digit `sel` that matches no `id` falls back to the list index. Examples: `P:requirements.mtow_g`, `P:components[battery].mass_g`. A path that does not resolve means "not found" (not an exception); a leaf must exist and not be `None`.

`recompute(rel_tol=None)`: `rel_tol` defaults to `load_claims_standards()["recompute_rel_tol"]["value"]` (step 9); a calculation's own `tol` overrides it for that calculation. For each claim, in file order, compute with these rules (this table is the whole status logic):
1. Value now. With `calc`: look up the calculation node and `resolve_calc(node["function"])`. Function not registered, or any input has no confirmed value (a `P:` path not found, or ANY undeclared `P:` input when `self.design is None`, or an input claim whose own value is `None`), then no value now: use the stored `claim.value` (may be `None`), and mark `unconfirmed = "calc function 'f' is not registered"` or `"input X has no confirmed value"`. Function registered: call it with the inputs (an input is a constant parameter's `value`, a PDL value, another claim's value now, or an assumption's `value`); an exception gives status FAIL with message `f"calculation {calc id} raised {type(e).__name__}: {e}"`; a result that lacks `claim.output` gives FAIL with `f"calculation {calc id} has no output {output!r}"`; otherwise the value now is `result[output]`. Without `calc`: the value now is `claim.value`.
2. Limit and margin. If the claim has `limit` and the value is numeric: resolve `limit.value` or the value of `limit.ref` (same lookup as an input); `margin(value, limit_value, op)`; `margin_abs = (limit_value == 0)`. Otherwise margin `None`, `margin_abs` False.
3. Self-check (proofs/1 rule 6): if the claim has a numeric value and numeric limit, then `(margin < 0)` must equal the plain comparison `not (value >= limit if op == ">=" else value <= limit)`; if not raise `ClaimGraphError(f"SELF-CHECK {id}: margin and plain comparison disagree")`.
4. Status, first rule that applies wins: margin below 0 gives FAIL (message `f"margin {margin_text(m, limit_value, unit, 1)}: {value} against {op} {limit_value}"`); a FAIL already set in step 1 stays FAIL; `unconfirmed` set gives PROPOSED (message = the reason; gate SKIP, which blocks; this is NOT STALE); the claim has `calc` and a stored number differs from the recomputed one (`claim.value`, or the calculation's `outputs[claim.output]`, compared with `close(stored, now, tol)`) gives STALE (drift only: the recomputed value is used for the margin; message `f"stored {stored}, recomputes to {now}"`); no `calc`, or declared `status: PROPOSED` gives PROPOSED (message `"no calculation: proposed, not verified"`); else PASS (message: `f"margin {margin_text(...)}"` when there is a margin, else `"computed, no limit"`).
`limit` in the result is `{"op": op, "value": limit_value}` or `None`. A claim is evaluated once per `recompute()` call (memoise inside the call only).

`explain(claim_id)`: unknown id or a node that is not a claim raises `KeyError(claim_id)`. Returns a flat list of dicts, depth-first from the claim, each `{"id", "type", "title", "depth", "edge"}` plus `value`/`unit` for claims and parameters (value as `recompute()`/PDL gives it) and `status` for claims; `edge` is the relation to the parent: `"derives-from"` (claim to its calc), `"uses"` (calc to each input node, including undeclared `P:` ids: type `parameter`, title the id), `"assumes"`, `"cites"` (parameter `source` entries that name a source, `cites` fields), `"verifies"` is NOT walked down (it points up to requirements; put them in the first item as `"verifies": [ids]`). Order: calc, then its inputs in declared order, then assumes, then cites. A node seen twice appears again, but its subtree is only expanded the first time (the repeat has `"repeat": true`).
