# U6.2 / T37: advisor pick for the T3.control_authority yaw fix (W11-A, D58)

Intent: every axis row of `T3.control_authority` reports a moment the motors can actually produce at hover with total upward thrust unchanged, and a row is only judged (PASS/FAIL) on physics the model covers. Source of the defect: reviews/2026-11-21-w3.md U3.6, row 7 and "Flag for advisor".

Actual (main 27d4fdd): `core/hangar/gates/discipline.py` `control_authority` computes `M_axis = sum_i |tau_i . e| * dT_i` with `dT_i = min(Tmax_i - T, T)`. It adds magnitudes as if each motor could push either way on its own. concept-a's four cant torques about `up` all have the same sign (-0.081, -0.082, -0.079, -0.080 N*m/N; a uniform pinwheel). That gives yaw 1.002 N*m, ratio 1.08, but with total thrust held the real cant-only yaw is 0.014 N*m. The same defect gives example-tailsitter-wing pitch 0.047 N*m, where the true value is 0 (both motors have the same pitch lever).

## Pick: (a) only. Constrained allocation, cant geometry only. No PDL change and no new threshold.

For each axis e in {pitch, roll, yaw} (axes as today), with T, Tmax_i, u_i, tau_i = (p_i - cg) x u_i as today:

    c_i = tau_i . e            a_i = u_i . up
    M_e(+) = max  sum_i c_i dT_i     s.t.  sum_i a_i dT_i = 0,  -T <= dT_i <= Tmax_i - T
    M_e(-) = max -sum_i c_i dT_i     (same constraints)
    M_e    = min(M_e(+), M_e(-))     ratio = M_e / m_wind   (m_wind unchanged)

- Solve with `scipy.optimize.linprog(method="highs")`. scipy is already a dependency (pyproject.toml). The problem is also a one-constraint fractional knapsack if the builder prefers no solver. If the solver reports infeasible, give the row M_e = 0.
- Hold only the net upward thrust. Do NOT also hold the other two moments at zero ("pure axis"). Without prop reaction torque, concept-a has no independent yaw mode, so pure-axis gives 0 on pitch and roll too (checked: it does).
- Also report, without judging, the yaw moment at equal hover thrust, `M0_yaw = T * sum_i tau_i . up`, in the yaw message and in `data["trim_yaw_nm"]`. For concept-a this is -1.06 N*m, which shows that the cant is unbalanced at hover.

Status rules (reads only fields that already exist: `propulsion.max_thrust_n`, `axis`, `role`, positions/geometry, mass; standards `hover_ctrl_factor`, `hover_wind_mps`, `wind_drag_coefficient`, `wind_moment_min_lever_fraction`, `pack_sag_fraction`, all as today):
- pitch, roll: PASS/FAIL on the ratio, as today. A pending criterion still SKIPs through `_judge`.
- yaw: PASS if the cant-only ratio >= hover_ctrl_factor. Otherwise SKIP with "not judged: yaw from prop reaction torque is not modelled (PDL has no spin/torque field)", `data.would_be = FAIL`, and the cant-only numbers in the message. Reason: every design without cant yaws through reaction torque, which the model omits, so a raw FAIL would block real quads after the D7 flip on 2026-12-08. In report-only mode a SKIP shows as WARN, as a FAIL does today.
- The yaw message also says "yaw wind moment uses the pitch/roll model (conservative)".

## Not picked
- (b) prop reaction torque: this needs two new optional PDL fields, `propulsion.spin` {cw, ccw} and `propulsion.torque_per_thrust_m` (kq) with `_source`. That is an additive minor schema version (1.0 -> 1.1, older files validate unchanged). It is the right v1.1 follow-up, but it is a schema change and every design would need sourced data. concept-a has a source, DBF-Combined redesign/qp/A/sitl/a_plant.py: KQ = 0.0204 m; spins LR, UL CCW and LL, UR CW. The c0 designs have none. Proposed as a new ledger item, not part of T37.
- (c) a yaw-specific wind moment: this needs a new horizontal-lever model input, which would be a new `pending` threshold. The current reuse overstates the yaw disturbance, which is conservative. Not needed for soundness.
- Subtract (drop the yaw row): this loses the concept-a signal below. Modify (sign-aware sum without the LP): not sound with unequal Tmax or levers. Adjust (raise or lower thresholds): not allowed and not the defect.

## Decision for the human (not a gate fix)
concept-a's plane.yaml cant is a uniform pinwheel, copied from the amodel CAD (`common.py motor_R = rotX(PHI) @ rotY(CANT)`, the same sense at every station). The source SITL plant (`sitl/a_plant.py` lines 147-148, `sin(CANT) * mspin[i]`) and the claims calculation CALC-A-YAW both assume the cant alternates with the spin direction. As drawn, hover leaves about 1.06 N*m of untrimmed yaw. Reaction torque is at most about 0.27 N*m with KQ 0.0204 and alternating spins, so the drawn cant cannot be trimmed. Either the CAD or plane.yaml is wrong, or the build is. This needs a design-engineer or human check (designs-only change), separate from T37.
