## Decision: where generated geometry lives (taken by W23-T; do not reopen)
Generated meshes are NOT stored. They are computed from the parameters on load and cached in memory by content key. Reasons, all checked in the code:
1. `*.stl` is Git LFS (`.gitattributes`): committed generated STLs would put a binary into every parameter change, and a `plane.yaml` edited by hand would leave a stale STL that no check notices.
2. Every consumer already asks one function: `geometry.component_parts(component, base_dir)` (mass, interference, strip planform, export GLB/STL, the studio viewer through `export.to_scene`, FEA through `fea._mesh`, `design.sweep` through `load_design`). Adding a `generator` branch there makes all of them work with no per-consumer change. The only direct file readers of `geometry.mesh.file` are `geometry._local_parts`, `geometry._base_key` and `fea.part_hash`; all three are handled below.
3. `mass_g` is read from `design.data` at 17 places. `load_design` resolves `mass_model` into `mass_g` once, so those places are unchanged.
4. Existing designs have no generator, no `parameters` and no `mass_model`: every new code path is skipped for them (acceptance test: `design.raw is None` and `data` identical for every committed design).
5. `design set` stays a one-file byte-preserving text edit plus one CHANGELOG block; "regenerates the affected meshes and masses" means: before writing, the op regenerates the affected components from the edited text, refuses the edit if any fails, and reports mass and CG before/after (a failed regeneration changes nothing on disk).
Cost: a CLI call regenerates the generated parts once (about 1 s per wing, measured 2.8 s for import + one wing core with a bore + loading the STL it is compared with). Cached in-process by content key. No on-disk cache in this brief.
