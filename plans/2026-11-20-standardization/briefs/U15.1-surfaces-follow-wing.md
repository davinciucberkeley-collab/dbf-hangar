At span 1800: pivot (868.37, 680, 21.51), axis (0.1586, 0.9816, -0.1064); the 7.87 mm x shift equals the measured 7.8 mm miss. Writing those values by hand into r-hinge and l-hinge at span 1800 clears both hinge rows.
5. Known limit (state it in the PR, do not fix it here): with the derived hinge, a400m-rc shows `T1.attachment_overlap` "range max of r-hinge (20 deg): parts overlap 2 %" (threshold `glued_overlap_max_fraction` 0.02) at span 1696 AND at 1800 (the hand axis had a hair more margin). The FAIL set is the same at both spans, so span 1800 adds nothing new; narrowing `range_deg` is a design change for the design-engineer.

## Decision (default taken; no schema_version bump, the schema change is a superset)
- (a) Planform: no code. Document that a surface's generator params reference shared `parameters`.
- (b) Derived hinge: new optional attachment field `hinge_from`, only value `"generator"`. When set on an attachment whose child is a `wing_panel` with `part: elevon` and `side` `left` or `right`, `resolve_design_data` replaces that attachment's `location`, `articulation.pivot` and `articulation.axis` in the RESOLVED data (never in the file; same pattern as `_cut_poses`) with the child generator's hinge line. `range_deg` and all other fields stay. The stored `location`, `pivot` and `axis` stay required by the schema and are a placeholder.
- Out of scope, defaulted: `tail_surfaces` elevator and rudder hinges (the tail planform can already follow `parameters`; the hinge derivation needs its own formula, a follow-up), servo/arm/rod/horn positions (U13.12 linkages). The plan text lists the elevator; the conductor should add a follow-up.

## Exact steps
1. `core/hangar/geom/wing.py`: add
```python
def hinge_line(params: dict, base_dir) -> tuple[list[float], list[float]]:
    """Two points (component-local frame, mm) of the hinge line of a wing_panel elevon, at elevon_y[0] and elevon_y[1] (signed by side)."""
```
Body: `p = fill_defaults(get("wing_panel"), params)` (from `hangar.geom.registry`); raise `GeometryError("hinge_from: ...")` when `p["part"] != "elevon"` or `p["side"] == "both"`; `p = {**p, "z_offset": p["z_offset"] + _placement_z(p)}`; `upper, lower = load_airfoil(p["airfoil_file"], base_dir)`; `h = p["hinge_frac"]`; `zm = float(_interp(upper, np.array([h]))[0] + _interp(lower, np.array([h]))[0]) / 2`; `s = -1 if p["side"] == "left" else 1`; for `y in (s * y0, s * y1)` with `y0, y1 = p["elevon_y"]`: `(x, z), = _place(np.array([[h, zm]]), p, y)`; return the two points `[x, y, z]`.
2. `core/hangar/geom/resolve.py`: add `_derive_hinges(data, base_dir, errors)` and call it in `resolve_design_data` right after `_cut_poses(data)`. For each attachment `a` in `data.get("attachments") or []` with `a.get("hinge_from") == "generator"`: `child` = the component whose id is `a["child"]`. If `child` is missing, is not generated `wing_panel`, `a["articulation"]` is not a dict, or `hinge_line(child["geometry"]["params"], base_dir)` raises `GeometryError`, `KeyError`, `TypeError` or `ValueError`: `errors.setdefault(str(a["child"]), "hinge_from: " + reason)` (reason: the exception text, or "child must be a wing_panel part elevon with side left or right and the attachment needs an articulation") and leave the attachment as written. Otherwise `T = hangar.geometry._transform(child)` (4x4, import inside the function as `_cut_poses` does), `p0, p1` = the two local points mapped by `T` (append 1.0, multiply, take the first three), `pivot = (p0 + p1) / 2`, `axis = (p1 - p0) / np.linalg.norm(p1 - p0)`, negate `axis` when `axis[1] < 0`; round every number with `round(float(v), 4)`; set `a["location"]` and `a["articulation"]["pivot"]` to the pivot list and `a["articulation"]["axis"]` to the axis list.
3. `schema/plane.schema.json`: in the attachment `properties`, after `kinematic_link` (about line 888), add `"hinge_from": {"const": "generator", "description": "v1.2, optional. generator = the resolved location, articulation.pivot and articulation.axis come from the child's wing_panel hinge line (part elevon, side left or right) and follow its parameters; the values written here are a placeholder. An aileron, flap or elevon hinge follows a wing change this way."}`. Regenerate `docs/pdl/reference.md` with `$PY -m hangar.cli schema docs --out docs/pdl/reference.md` (check the flag with `--help`).
4. `docs/team-guide.md`, section "Starting a new concept": add one bullet right after the "Many edits at once" bullet (8 lines at most): control surfaces that share a wing's planform put the shared numbers in `parameters` (for example `span_mm`, `root_chord_mm`, `tip_chord_mm`, `sweep_deg`) and reference them as `"$span_mm"` in the wing and in every aileron, flap or elevon `wing_panel`; `plane design set <path> parameters.span_mm --value N --why ...` then regenerates all of them; add `hinge_from: generator` to the hinge attachment of each such surface (side left or right) so its location, pivot and axis follow too.
