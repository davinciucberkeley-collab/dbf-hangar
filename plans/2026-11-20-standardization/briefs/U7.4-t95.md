## What the diff does (behaviour fixed here)
1. Schema `schema/plane.schema.json`: `schema_version` enum gains `"1.1"` (description says what 1.1 adds); title `Plane Design Language v1.1`; `propulsion` gains three optional fields: `spin` (`cw` or `ccw`), `torque_per_thrust_m` (number, exclusiveMinimum 0, N*m per N), `torque_per_thrust_m_source` (string, minLength 1). `additionalProperties: false` stays, so a typo is still an error.
2. Versions `core/hangar/migrate.py`: `KNOWN_VERSIONS` ends `"1.0", "1.1"`, `LATEST = "1.1"`. `migrate()` moves any older version to 1.1 (notes `schema_version <v> -> 1.1`, `no fields added, removed or renamed (all 1.0 blocks and 1.1 fields are optional)`; an already-1.1 file returns `already 1.1`). `bump_version_text` now also accepts a `1.0` line and writes `"1.1"`, touching only that line (CRLF and comments kept). `plane design migrate` therefore proposes 1.0 to 1.1 for the six committed designs (all at 1.0); migrating is optional, a 1.0 file validates unchanged. `core/hangar/ops/schema.py` needs no change (it reads `LATEST`). `core/hangar/importers/dbf.py:457` still writes `schema_version: "1.0"` (unchanged on purpose; a 1.0 file is valid).
3. `core/hangar/checks.py` `tier0_schema`: if any component's `propulsion` has `spin`, `torque_per_thrust_m` or `torque_per_thrust_m_source` and the file's `schema_version` is below 1.1, `T0.version` FAILs with `propulsion.spin, ... need schema_version "1.1"` (same pattern as the 0.2 to 1.0 rules).
4. `core/hangar/gates/discipline.py` `control_authority`: new helper `_reaction(active)` returns the signed reaction torque per unit thrust of each active lift motor, `+kq` for `cw`, `-kq` for `ccw`, or `(None, reason)` when any active motor lacks `spin`, `torque_per_thrust_m` or `torque_per_thrust_m_source` (reason `motor <id>: propulsion.<field> missing`). When it returns a list, the yaw cost vector of the D58 linear program becomes `c_i = tau_i . up + k_i * a_i` (`a_i = u_i . up`; the reaction torque acts along the thrust axis, so its part about `up` is `k_i * (u_i . up)`); `trim_yaw_nm` uses the same `c_i` (`T * sum c_i`); the yaw message says `cant geometry and prop reaction torque`; and the yaw row is judged (PASS/FAIL through `_judge`), never SKIP-with-would_be. When it returns `None`, nothing changes except the SKIP text, which keeps `prop reaction torque is not modelled` and now ends `(motor <id>: propulsion.<field> missing)`. Pitch and roll rows are untouched.
5. Docs: `docs/pdl/README.md` version table gets a 1.1 row and the heading `Move an old file to the latest version`; `docs/pdl/reference.md` is generated from the schema (regenerate, never edit).
6. Tests: `tests/test_pdl.py` (version strings 1.0 to 1.1 where the latest version is meant, 1.0 added to the migrate-notes cases, and 7 new cases), `tests/test_design_edit.py` (one assertion: the migrated concept-a file now carries `"1.1"`), `tests/test_discipline_gates.py` (5 new tests, 7 cases).

Physics sentence to check against the code before you commit (sign convention): `spin` is the sense of the prop seen from the side the thrust force points to, looking back at the motor (a hover lift motor: seen from above). A `ccw` prop turns along `+axis` (right-hand rule), so the airframe feels the reaction `-kq * T * axis`; a `cw` prop gives `+kq * T * axis`. That is the convention DBF-Combined uses (`sitl/a_plant.py` line 151 `-mspin[i] * Qt` with CCW = +1; BUILD-GUIDE-A.md line 833 "seen from the thrust side"). The diff encodes it as `(1.0 if spin == "cw" else -1.0) * kq`. If you read the code and find the opposite, stop and report.

Defaults taken (the plan and ledger text leave these open):
- Source field: `torque_per_thrust_m_source`, a sibling string like `flight.cruise_ld_source` and `flight.transition_speed_source` (the repo's `_source` convention: the gate reads it and SKIPs when it is missing). `spin` has no source field (it is a build fact, not a number).
- All three fields are required on EVERY active lift motor (up component at hover) for the yaw row to be judged; one motor lacking one field keeps the D58 SKIP for the whole yaw row, with the reason in the text. The user instruction was "every motor has both fields"; the source field is added because the repo's convention demands it.
- Reaction torque is added to the yaw row only. For a canted motor it also has a small pitch/roll part (`kq * sin(cant)`, at most about 0.005 N*m per N for concept-a's 14 degree cant and kq 0.0204 m); it is left out as negligible against the cant lever and the instruction scoped the change to yaw. It is not modelled and not claimed.
- When the fields are present and complete, a yaw ratio below `hover_ctrl_factor` is a real FAIL (not SKIP). After the D7 flip on 2026-12-08 that blocks; before it, report-only shows WARN, as for pitch and roll. A pending `hover_ctrl_factor` still gives SKIP through `_judge`.
- `trim_yaw_nm` includes the reaction torque at equal thrust (zero for balanced spins, `+-4 kq T` for four equal spins).
- T99 part 3 (propose a criterion for the untrimmed yaw moment at equal thrust) is NOT done here: it needs a new threshold in `standards/operations.yaml` (value pending a source) and a decision on what the gate should say; the yaw row still only reports `trim_yaw_nm`, not judged.
